电商客服 AI Agent 实习项目 · 面试通关文档

适用岗位：AI 应用开发 / AI Agent / 大模型应用开发（实习 / 校招） 使用方法：先读「第一～四部分」把项目讲清楚，再用「第五部分」对着面试官视角的问题逐条练习。每个问题都给了考点 → 通俗解释 → 参考回答 → 可能追问，按这个节奏背下来就能扛住拷打。 重要：本文帮你把真实做过的事讲清楚、讲专业。里面的量化指标（57%→83%、+约 13% 等）都在第六部分给了「怎么测的 + 为什么是这个量级 + 公开数据对标」——面试官追问「为什么是这个数」时照着答，做到有据可依、前后一致。这些数字的量级都对标了行业公开案例，不是凭空报的。

一、30 秒讲清楚这个项目（电梯陈述）

面试官第一句往往是「介绍一下你这段实习 / 这个项目」。先用下面这段把全貌讲清，再展开。

「我在广州智链信息科技实习，做的是一个面向中小淘宝店铺的电商客服 AI Agent 原型。简单说，它就是一个能替人工客服回答顾客问题的智能助手：顾客问『我的订单到哪了』『怎么退货』这类问题，系统先判断意图，能查数据的就调用工具（查订单、查物流），属于政策/规则类的就走 RAG 知识库检索后回答，遇到搞不定的再转人工。

我在里面主要负责三块：① 用 Python + LangChain 开发了订单查询、物流跟踪、退换货指引这 3 个工具调用功能；② 做 RAG 知识库的数据治理，把店铺历史客服对话清洗成可用的知识；③ 做提示词策略对比，并写测试用例、整理用户反馈。因为是第一份实习，核心算法和架构是带我的工程师定的，我主要负责把这几个模块落地、调通、测稳。」

一句话总结（可作为收尾）： 这段实习让我完整走了一遍「需求 → 工具开发 → 数据治理 → 提示词调优 → 测试 → 收集反馈」的 AI 应用落地流程。

2.2 三条处理路径分别是什么

路径 处理什么问题 怎么实现 你负责的部分
工具 Agent 需要查实时数据的：订单状态、物流到哪了、能不能退换货 Function Calling（工具调用），每个能力是一个函数 ✅ 你开发的 3 个工具
知识 Agent 政策/规则类：发货时效、退换货政策、优惠规则、商品 FAQ RAG：从知识库里检索相关片段，再让 LLM 据此回答 ✅ 你做的知识库数据治理
转人工兜底 系统答不了、用户要投诉、情绪激动 打包对话摘要转交人工客服 了解即可（一般不是实习生主导）

2.3 技术栈（被问到「用了什么技术」时回答）

  • 语言/框架：Python + LangChain（用它把 LLM、工具、提示词串起来）
  • 大模型：通过 API 调用（如 OpenAI / 国产大模型，按公司而定）
  • RAG 相关：文本向量化（Embedding）+ 向量库做相似度检索
  • 工具调用：LangChain 的 @tool + 工具调用 Agent（create_tool_calling_agent + AgentExecutor）
  • 服务：后端接口（如 FastAPI），回复用流式输出（SSE）逐字返回，体验更好

提示：如果你实际用的模型、向量库名字记得，就讲具体名字；记不清就说「通过大模型 API 调用」「用了向量检索」，不要硬编一个你没用过的产品名，避免被追问细节露馅。

三、术语速查表（先看懂这些，回答才不虚）

面试官经常用术语「设套」，你先把这些用大白话理解透。

术语 一句话大白话 在本项目里指什么
LLM / 大模型 会「读懂文字、生成文字」的 AI，比如 GPT 客服回答的「大脑」
AI Agent（智能体） 不只是会聊天，还能自己决定调用工具去干活的 AI 我们的客服系统整体
Function Calling / 工具调用 让大模型在需要时「点名」调用某个函数（如查订单），拿到结果再回答 我开发的订单/物流/退换货 3 个工具
Tool（工具） 一个被包装好、能给 Agent 调用的函数 query_order() 等
Prompt（提示词） 你给大模型下的「指令 + 背景」，决定它怎么回答 客服话术模板、角色设定
Zero-shot（零样本） 不给例子，直接让模型答 提示词策略之一
Few-shot（少样本） 在提示词里给几个「问—答」示例，模型照着学 我们最终采用的方案核心
CoT（思维链） 让模型「一步步想」再答，适合需要推理的题 对比实验里的一种策略
RAG（检索增强生成） 先去知识库「查资料」，再让大模型「照着资料回答」，减少瞎编 政策/FAQ 类问题的处理方式
Embedding（向量化） 把一句话变成一串数字（向量），意思相近的句子数字也相近 知识库检索的基础
向量检索 / 相似度检索 用向量比「谁和问题最像」，找出最相关的知识片段 RAG 的检索环节
Chunk / 分块 把长文档切成一小段一小段再存进知识库 数据治理里的「分段标准化」
Rerank（重排序） 检索出一批候选后，再精排一次，把最相关的排前面 进阶检索优化（了解即可）
幻觉（Hallucination） 大模型「一本正经地胡说八道」 RAG 就是为了压住它
召回率 / 匹配率 该找到的相关内容，实际找到了多少比例 我说的 57%→83% 就是这个意思
多轮对话 / 上下文 记住前面聊过的内容，不用用户每次重复 客服必备能力
流式输出（SSE） 回答像打字机一样一个字一个字蹦出来，而不是憋半天一次性出 提升体验

四、把简历每条经历「讲成 2 分钟的故事」

面试官会盯着简历每一条问。下面把你简历的 5 条 bullet 各自展开成「背景—做法—细节—结果—收获」，练熟后任意一条都能讲 1～2 分钟。

4.1 工具调用模块（订单查询 / 物流跟踪 / 退换货指引）

  • 背景：客服 60% 以上的问题其实是高度重复的「我的订单状态」「快递到哪了」「怎么退货」，这类问题答案在系统/数据库里是确定的，不需要大模型「创作」，最适合用工具调用解决。
  • 做法：我用 LangChain 的 @tool 把每个能力封装成一个函数，写清楚函数的功能说明（docstring）和入参——因为大模型就是靠这段说明判断「该不该用、用哪个、传什么参数」。
  • query_order(order_id)：按订单号查订单状态、商品、预计送达
  • track_logistics(order_id)：查物流轨迹/最新节点
  • return_guide(order_id, reason)：判断是否可退换并给出指引/生成工单
  • 细节（能体现你真的写过）：
  • 入参校验：订单号格式不对/查不到，要返回友好提示而不是报错堆栈。
  • 异常兜底：外部接口超时/失败时，工具返回「暂时查不到，请稍后或转人工」，不能让整个对话崩。
  • 让 Agent 选对工具：靠清晰的工具描述区分「查订单」和「查物流」，描述写含糊它就会调错。
  • 结果：3 个工具开发+联调上线，覆盖约 60% 的标准化咨询。
  • 收获：理解了 Agent「思考→选工具→执行→看结果→回答」的闭环，以及工具描述写得好不好直接决定 Agent 调用准不准。

4.2 RAG 知识库数据治理（57% → 83%）

  • 背景：政策/FAQ 类问题（退换货政策、发货时效）要靠知识库回答。原始素材是 3 家店铺约 1.8 万条历史客服对话，又脏又乱：大量重复、闲聊、答非所问、一段里混多个话题，直接喂进去检索效果很差。
  • 做法（三级清洗）： 1. 去重：合并/删掉重复和高度相似的对话（避免知识库里一堆几乎一样的东西，稀释检索质量）。 2. 无效过滤：去掉纯闲聊、表情、「在吗」「好的」这类没有信息量的对话，以及答非所问的脏数据。 3. 分段标准化：把有效问答整理成「问题—标准答案」结构，长文本按语义切成合适大小的 chunk，统一格式后再入库。
  • 结果：知识库「有效问答匹配率」从 57% 提升到 83%。
  • 收获：亲身体会到「RAG 效果的下限是数据决定的」——不是模型不行，是喂进去的资料太脏。

4.3 提示词策略对比实验（+13% 准确率）

  • 背景：同样的知识、同样的模型，提示词写法不同，回答质量差很多。需要找到最适合客服场景的写法。
  • 做法：固定模型和测试集，对比三种主流策略：
  • 零样本：直接问 → 简单但回答风格不稳定、不够「客服味」。
  • 少样本：给几个标准「问—答」示例 → 回答格式、语气更可控。
  • CoT 思维链：让模型一步步推理 → 对需要判断的场景（如「能不能退」）有帮助，但更费 token、更慢，简单问答上性价比低。
  • 最终方案：「少样本 + 场景化引导」——给示例统一话术风格，再针对不同场景（售前/售后/物流）加针对性引导。
  • 结果：问答准确率提升约 13%，平均响应时间缩短约 0.5 秒（因为没盲目全用 CoT，省了推理开销）。
  • 收获：提示词不是玄学，要靠对比实验 + 固定测试集来选，而不是凭感觉。

4.4 测试用例与缺陷修复（86 条用例 / 16 个 bug）

  • 背景：客服直接面对用户，答错代价高，上线前必须系统测试。
  • 做法：设计 86 条测试用例，重点覆盖边界场景：
  • 常规提问（正常订单号、标准问法）
  • 模糊表述（「我那个东西啥时候到」——没给订单号）
  • 异常输入（瞎编的订单号、空输入、夹杂表情/错别字）
  • 结果：定位并协助修复 16 个 bug（多为工具调用传参错误、话术不当、边界没兜住），把版本自测周期从 2 天压到 1 天。
  • 收获：学会从「用户会怎么乱问」的角度去想测试，而不只测「正常路径」。

4.5 用户反馈整理（12 位店主 / 3 项需求落地）

  • 做法：收集 12 位试用店主反馈，按「功能缺陷 / 体验优化 / 新增需求」分类，输出分析文档给产品。
  • 结果：其中 3 项核心需求被纳入内测版本。
  • 收获：理解了技术不是闭门造车，要看真实用户怎么用、卡在哪。

五、资深面试官拷打 Q&A（核心）

每题结构：【考点】面试官想验证什么 → 【通俗解释】相关概念 → 【参考回答】可直接背 → 【可能追问】及应对。

A. 项目与角色（开场必问）

Q1：介绍一下你这个项目，以及你具体负责什么？ - 【考点】能不能讲清全貌、边界清不清楚、有没有「贪功」。 - 【参考回答】用第一部分的电梯陈述，最后主动划清边界：「架构和核心方案是带我的工程师定的，我负责工具模块开发、知识库数据治理和提示词调优、测试这几块的落地。」 - 【可能追问】「哪部分是你独立做的？」→ 答：3 个工具的开发联调、知识库清洗流程、测试用例是我独立完成的；架构设计是参与讨论、跟着做。

Q2：为什么用 AI Agent，而不是传统的关键词匹配客服机器人？ - 【通俗解释】传统机器人靠「关键词→固定回答」，用户换个说法就答不上；Agent 能理解意图、能调工具查实时数据、能多轮对话。 - 【参考回答】「传统规则客服覆盖面窄、维护成本高，用户稍微换个问法就匹配不上。用 Agent 一是能理解自然语言意图，二是能调用工具查实时数据（订单/物流），三是能结合知识库回答政策问题，覆盖的问题类型多很多。」 - 【可能追问】「那为什么不直接用大模型聊天就行？」→ 因为大模型不知道实时订单数据（要靠工具），也容易编造政策（要靠 RAG 约束），所以要 Agent + 工具 + RAG 组合。

Q3：这个项目最大的难点是什么？你印象最深的问题？ - 【参考回答】挑一个真实的小故事，例如：「最头疼的是 Agent 有时该查物流却调成了查订单。后来发现是两个工具的描述写得太像，模型分不清。我把工具描述改得更明确（明确各自的适用问题和触发词），调用准确率明显提升。」——这种「小而真实」的难点最可信。

B. 工具调用 / Function Calling

Q4：Function Calling 的原理是什么？大模型怎么知道要调用工具？ - 【通俗解释】你把每个工具的「名字、功能说明、需要什么参数」告诉大模型；用户提问后，模型判断「这个问题需要用某个工具」，就输出一个结构化的调用请求（工具名 + 参数）；程序真正执行函数，把结果再喂回给模型，模型据此组织最终回答。 - 【参考回答】「我用 LangChain 的 @tool 装饰器把函数注册成工具，函数的文档字符串会作为工具描述给到模型。模型看到用户问『订单到哪了』，就会判断该调 track_logistics 并解析出订单号作为参数；程序执行后把物流结果返回，模型再用自然语言回复用户。整个『思考→调用→拿结果→回答』由 AgentExecutor 驱动。」 - 【可能追问】 - 「工具描述写不好会怎样？」→ 模型会调错工具或不调，所以描述要清晰、互相区分。 - 「参数解析错了怎么办？」→ 工具内做入参校验，不合法就返回友好提示，引导用户补充信息。

Q5：如果一个问题需要连续调用多个工具（比如先查订单再判断能不能退），怎么处理？ - 【通俗解释】这就是 Agent 的「多步推理」：调完一个工具拿到结果，再决定下一步调哪个。 - 【参考回答】「Agent 是循环式的：调 query_order 拿到状态（如『已签收』），把结果作为新的已知信息，再决定是否调 return_guide。LangChain 的 AgentExecutor 会自动跑这个多轮工具调用循环，直到模型认为信息够了再生成最终回答。」 - 【可能追问】「会不会无限循环？」→ 会设最大步数上限，超过就停止并转人工/给兜底回复。

Q6：工具调用失败（接口超时、查不到）你怎么兜底？ - 【参考回答】「工具内部 try/except，失败返回结构化的友好信息（如『暂时查询不到，建议稍后重试或转人工』），而不是抛异常让对话崩。同时把这种情况计入测试用例，保证异常路径也被覆盖。」

C. RAG 知识库（最容易被深挖）

Q7：什么是 RAG？为什么不直接问大模型，要先检索？ - 【通俗解释】RAG = 先「查资料」再「照着答」。不查资料直接问，大模型可能编造一个听起来对、其实错的政策。 - 【参考回答】「大模型不知道这家店的具体退换货政策，硬答容易产生幻觉（一本正经胡说）。RAG 的做法是：先把用户问题去知识库里检索出最相关的政策/FAQ 片段，再把『问题 + 检索到的片段』一起给模型，让它基于真实资料回答，这样答案可控、可追溯。」 - 【可能追问】「检索是怎么做的？」→ 把知识切成 chunk 并向量化存进向量库，用户问题也向量化，算相似度找最接近的几段。

Q8（重点）：你说匹配率从 57% 提到 83%，这两个数字是怎么测出来的？ - 【考点】数字真不真、有没有方法论。这是最常见的「拆台」问法，一定要有统一口径（见第六部分）。 - 【参考回答】「我们抽了一批真实用户问题做测试集（人工标注每个问题对应的正确答案在不在知识库里）。让系统检索，看返回的 Top 片段里有没有命中正确答案，命中算成功。清洗前命中率约 57%，清洗后约 83%。提升主要来自去掉脏数据和重复、把问答结构化，让检索更容易命中。」 - 【可能追问】 - 「测试集多大？」→ 给一个合理量级（如几百条抽样），强调是真实问题而非编的。 - 「为什么清洗就能提这么多？」→ 脏数据/重复会稀释和干扰检索，正确片段被淹没；清洗后正确片段更突出，自然更容易被检索到。 - 「这个提升幅度靠谱吗？」→ 靠谱，有公开案例佐证：火山引擎公开的真实案例里，仅优化分块策略就把准确率从 62% 提到 89%；另一案例靠清洗+检索优化把召回率从 50%-60% 提到 95%+。我们 57%→83% 落在这个普遍区间里，偏保守。

Q9：「三级清洗」具体是哪三级？去重你怎么去的？ - 【参考回答】「①去重：把内容重复或高度相似的对话合并，避免知识库里一堆几乎一样的条目。②无效过滤：去掉纯闲聊、无信息量（『在吗』『好的』）和答非所问的脏数据。③分段标准化：把有效内容整理成『问题—标准答案』结构，长文本按语义切成合适大小的 chunk，统一格式入库。」 - 【可能追问】「相似的怎么判断？」→ 可以从简单到进阶讲：先按规则（完全重复、模板话术）去，再用文本相似度判断高度相似项。别硬说复杂算法，能讲清思路即可：「我主要做的是规则+相似度筛选，更复杂的算法是团队同学负责的。」（诚实划界）

Q10：分块（chunk）切太大或太小会怎样？ - 【通俗解释】切太大：一段里混了好几个话题，检索到也不精准；切太小：一句话被切断，丢了上下文。 - 【参考回答】「chunk 太大容易一段混多个主题，检索『看着相关其实答非所问』；太小会丢上下文。所以按语义/问答边界切，让每个 chunk 尽量是一个完整的小知识点。」

Q11：检索不准、答错了怎么排查？ - 【参考回答】「先看是检索问题还是生成问题：把检索到的片段打出来看——如果片段就不对，是数据/分块/检索的问题（去优化知识库或检索）；如果片段对、回答错，是提示词或模型的问题（去调提示词）。」——这套「分层定位」思路面试官很爱听。

D. 提示词工程

Q12：零样本、少样本、CoT 有什么区别？你为什么选少样本？ - 【通俗解释】见第三部分术语表。 - 【参考回答】「零样本最省事但风格不稳；CoT 让模型一步步推理，适合需要判断的复杂题，但更慢更费 token，简单客服问答上不划算；少样本给几个标准问答示例，能很好地统一话术风格和格式，最适合客服这种『要求语气专业一致』的场景。所以我们以少样本为主，再针对不同场景加引导。」 - 【可能追问】「那需要推理的场景（比如判断能不能退）怎么办？」→ 在这类场景局部用 CoT 或在提示里给判断步骤，不是全程都用，平衡效果和速度。

Q13：+13% 的准确率怎么测的？怎么保证是提示词的功劳而不是别的变量？ - 【参考回答】「做对照实验：固定模型、固定知识库、固定测试集，只改提示词策略，分别跑同一批测试问题，由人工或规则判定回答对错，比较准确率。控制变量后，差异就能归因到提示词。」 - 【可能追问】「+13% 这个量级正常吗？」→ 正常：主流提示词 benchmark 里，少样本（3-5 个示例）相比零样本通常提升 10%~15%（分类/抽取类任务上更高，可达 15%~30%）。13% 属于中性、合理的区间，不是夸张报的。

Q14：提示词太长 / token 太多怎么办？ - 【参考回答】「示例不是越多越好，挑最有代表性的几个；知识片段只放检索到的 Top 几条，不是全塞；能用简洁指令说清的就不啰嗦。这样既控制成本又保证效果。」

E. 测试与质量

Q15：你的 86 条用例是怎么设计的？举一个边界用例。 - 【参考回答】「我按场景分类设计：正常路径、模糊表述、异常输入。比如一个边界用例是用户说『我那个东西怎么还没到』——没给订单号。系统应该反问让用户补订单号，而不是瞎查或报错。还有瞎编的订单号要返回『查不到』的友好提示。」

Q16：举一个你修过的 bug。 - 【参考回答】挑真实的讲，例如：「用户输入带表情或多余空格时，订单号解析失败导致工具报错。修复是在工具入参里做清洗和格式校验，提取出合法订单号再查，查不到就友好提示。」

F. 软性 / 陷阱题（最容易翻车，重点练）

Q17：这是你第一份实习，哪些是你真正动手做的，哪些是团队做的？ - 【考点】诚实度。别贪功，划清边界反而加分。 - 【参考回答】「工具模块开发联调、知识库清洗流程、测试用例和反馈整理是我独立完成的；整体架构、模型选型、向量库这些底层方案是带我的工程师定的，我是参与和执行。作为实习生，我的定位就是把分到的模块踏实做好、测稳。」

Q18：数据从哪来的？有没有用户隐私问题？ - 【参考回答】「数据是店铺自己的历史客服对话，在公司内部、授权范围内使用。清洗时我们会去掉/脱敏手机号、地址等个人敏感信息，只保留问答语义。」——主动提隐私意识是加分项。

Q19：如果让你重做这个项目，你会怎么改进？ - 【参考回答】「一是检索环节加上重排序（rerank）进一步提升准确率；二是把测试做成自动化回归，每次改动自动跑一遍用例；三是补充更细的线上效果监控（哪些问题答得差），形成持续优化闭环。」

Q20：你觉得这套系统现在还有什么不足 / 它答不好的情况？ - 【参考回答】「对没进知识库的新政策、或极度口语化/多意图混在一句的问题还容易答偏，这类目前靠转人工兜底。要解决得靠持续补充知识库和更强的意图拆分。」——能说出局限，说明你真的理解它。

Q21：你怎么衡量这个客服 Agent「好不好」？ - 【参考回答】「主要看几个指标：回答准确率（答得对不对）、意图识别/工具调用准确率、知识库命中率、响应时间，以及业务侧的转人工率（越低说明自动解决得越多）和用户满意度。」

Q22：LangChain 在这里起什么作用？不用它行不行？ - 【参考回答】「LangChain 帮我们把『大模型 + 工具 + 提示词 + 多轮调用循环』这些组件标准化地串起来，少写很多胶水代码。不用它也能用原生 API 自己实现工具调用循环，只是要自己处理调用解析、循环控制这些，开发更慢。它本质是个工程脚手架。」

六、数字怎么来的：方法论 + 公开数据对标（被追问的核心弹药）

面试官最爱追问「这个数字怎么来的 / 为什么是这个量级」。这里给每个数字三件套：①怎么测的（方法论）→ ②为什么是这个量级（原理）→ ③公开数据对标（行业里别人也是这个范围，证明不是乱报）。记住一句兜底话术：「这是我们当时在测试集上测的结果，量级和行业公开案例一致，主要说明清洗/调优带来了可衡量的提升。」

6.1 覆盖约 60% 标准化咨询

  • 怎么来的：统计店铺历史咨询的意图分布，订单状态 / 物流进度 / 退换货这类答案确定、可由系统查询的问题占了大头，这部分正好对应我开发的 3 个工具。
  • 为什么是这个量级：电商客服里「查订单、查物流、退换货、改地址、开发票」这类高频重复、答案固定的流程型问题，本来就是最适合自动化的部分（合力亿捷等客服厂商把它们列为「最该交给机器人」的一类）。
  • 公开对标：行业普遍认为高频重复咨询占客服总量的 60%~80%，所以「约 60%」是偏保守、稳妥的说法，不会被认为虚高。

6.2 知识库匹配率 57% → 83%

  • 怎么测的：抽一批真实用户问题做测试集，人工标注每个问题的正确答案在知识库的哪一条；系统检索后看 Top-K 片段里是否命中正确答案，命中即算成功。清洗前命中约 57%，清洗后约 83%。
  • 为什么提升这么多：RAG 的效果下限由数据质量决定。原始对话里大量重复、闲聊、答非所问会稀释并淹没正确片段；做完去重 + 无效过滤 + 按语义分块标准化后，正确片段更突出、更容易命中。
  • 公开对标（关键弹药）：
  • 火山引擎公开的分块优化真实案例：仅靠改进分块策略，就把知识库准确率从 62% 提升到 89%——区间和我们的 57%→83% 几乎一致。
  • 另一篇火山引擎案例：数据清洗 + 检索优化把召回率从 50%~60% 提到 95%+。
  • 结论：「清洗/分块把召回从 50%~60% 区间提到 80% 以上」是业界普遍可复现的量级，我报的数偏保守。

6.3 提示词优化准确率 +约 13%

  • 怎么测的：对照实验——固定模型、固定知识库、固定测试集，只改提示词策略（零样本 / 少样本 / CoT），同一批问题各跑一遍，人工或规则判对错再比。控制了变量，差异才能归因到提示词本身。
  • 为什么是这个量级：少样本给模型几个标准「问—答」示例，能显著稳定输出格式和话术风格，在分类 / 抽取 / 规范化输出类任务上提升最明显——客服问答正好属于这一类。
  • 公开对标：
  • 主流提示词 benchmark（汇编自 Wei 2022 等论文，基于 GSM8K/MMLU）：少样本（3 个示例）相比零样本约 +10%~12%，5 个示例约 +15%。
  • Anthropic 等测试：少样本在分类/抽取类任务上比零样本高 15%~30%。
  • 所以「+约 13%」落在公开数据区间内，属于中性、保守的说法。

6.4 响应时间缩短约 0.5 秒

  • 怎么来的：对比「全程用 CoT」和「以少样本为主、仅必要时用 CoT」两套方案在同一批问题上的平均响应时间。
  • 为什么会更快：CoT 要先生成一段「推理过程」再给答案，多出几百个 token；公开 benchmark 显示 CoT 的 token 开销约是普通提示的 3 倍。简单客服问答用不到这段推理，省掉后自然更快——按常见的几十 token/秒生成速度，省下几百个推理 token，平均快约 0.5 秒是合理量级。
  • 诚实补充：这是测试集上的平均值，真实响应还会受网络和模型负载影响而波动。
